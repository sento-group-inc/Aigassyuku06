なぜ分身OSを作るのか

AIを「便利な質問箱」から「仕事を任せる相手」に変える。

何が見えるようになるかAIが何を知っている状態で動くかが見える。
今やること毎回の説明をAGENTS.mdへ移し、次回から省略できる。
全員が同じようにできるか10人全員が同じフォルダ構成で再現できる。
あるあるAIに毎回「うちの会社は…」から説明して、作業前に疲れる。
だからまず個人OSとして、自分の会社・判断軸・仕事の型を外に出す。
終わるとAIへの説明が減り、業務改善HTMLのような見える成果に時間を使える。

あのね、みなさんAIを使ってるじゃないですか。ChatGPTに聞く。Claudeに聞く。資料を作らせる。メール文を直させる。それ自体はもう珍しくないんですよ。

でも、たぶん同時にこういう感覚もあると思ってて。毎回、説明してませんか。「うちの会社はこうで」「このお客さんはこうで」「僕はこういう判断をしたくて」「この表現はうちっぽくないからやめて」。

社員を雇ったとして、毎朝その人に「うちの会社は何をしている会社です」から説明し直してたら、仕事にならない。でもAIにはそれをやっている。この「再説明コスト」をゼロにする。それが今日と明日でやることです。

さらに一歩先の話をすると、1人のAIに全部やらせるより、役割分担したAIチームに任せる方が質が上がります。文章を書くAI、それをレビューするAI、タスクを割り振るAI——それぞれが専門領域を持ったチームとして動く。この合宿の最終地点は、あなたがそのAI組織のCEOになることです。

AIに毎回背景を説明し、出てきたものを場当たり的に直す。再説明コストが積み上がる。

After

引き継ぎ書（AGENTS.md群）を渡したAIチームが、業務の文脈を読んで自律で動く。あなたはCEOとしてレビューと判断だけをする。

今日作るのは「全自動で放置する仕組み」ではなく、引き継ぎ書を渡し、仕事を任せ、レビューして育てる環境です。
合宿での対話型ガイドについて
講義HTMLを見ながら、Claude/Codexと対話してAI組織を構築するガイドファイルが journey/ フォルダにあります。「journey/README.md を読んで始めてください」と言えばCEOへの道が始まります。
10社の社長が集まる合宿なので、最初からチーム標準にはしません。まず各自の個人OSを作る。その先で、組織では改善を個人メモに閉じず共有標準へ戻します。詳しくは 個人OSからチーム標準へ。

grill-me型プロンプトで業務を深掘りする

方針が未定でも大丈夫。AIに執拗にインタビューさせて、深層心理から言語化する。

あるある「やりたいことは？」と聞かれても、頭の中ではまだ屏風の虎みたいにぼんやりしている。
だからAIにしつこく質問させて、足りないInputと判断軸を外に出す。
終わると「なんとなく」ではなく、Codexに渡せる業務の骨格ができる。
方針が未定でも大丈夫 「何を作るかまだ漠然…」でも始められる。AIが質問を連打して言語化を手伝う。推奨回答も出してくれるので、答えられなくてもOK。
深層心理まで掘り下げられる 自分では気づいていない前提・判断軸・詰まりが出てくる。「任せたい作業」ではなく「本当の課題」が見える。
AGENTS.mdに直結する インタビュー結果がそのままAGENTS.md / state.md / memory.mdに変換できる。深掘りが環境構築の最初の一歩になる。

3

IPOAで「なにをやりたい」の手前を定義する

Outputから始めず、Actionから逆算して必要なInputを決める。

あるある「BIを作りたい」と言うけど、見た後に誰が何を決めるかは曖昧なまま。
だからActionから逆算して、Output、Input、Processを決める。
終わるとAIに頼むものが「それっぽい資料」ではなく、行動につながる成果物になる。

IPOAは Action から逆算する

flowchart TB A["Action\n誰が何を決めるか"] --> O["Output\n何が見えれば動けるか"] O --> I["Input\n判断材料は何か"] I --> P["Process\nどう変換・分析するか"] P --> O

弱い入口

「BIを作りたい」「ダッシュボードがほしい」。これはOutput名だけで、行動が決まっていない。

強い入口

「毎週月曜に赤字見込み案件を3件選び、担当者に次の一手を決めさせたい」。Actionがあるので必要なOutputが決まる。

さっき覚えたgrill-meの型でIPOAを深掘りする
この業務について、IPOAで深掘りしてください。

順番:
1. Action: 誰が、いつ、何を決める・動くべきか
2. Output: そのActionに必要な見える成果物は何か
3. Input: 判断材料として何の情報が必要か
4. Process: Inputをどう整理・分析・変換すればOutputになるか

各質問に対して、私が答えやすい推奨回答も提示してください。
最後に ipoa.md と work-improvement.html に変換できる形で整理してください。
詳細ページ: IPOAフレームワーク

Claude CodeからCodexへ引っ越す

すでにClaude Codeを使っている人は、育てた資産を捨てずに移す。

あるあるClaude Codeで育てたルールがあるのに、Codexでまたゼロから説明するのはもったいない。
だから既存のCLAUDE.mdやSkillを棚卸しし、Codex用に移す。
終わると道具を変えても、自分の判断軸と作業ログは引き継げる。
この章の目的Claude Codeで作ったルール、Skill、作業ログをCodexでも使える材料に変える。
ここでやることClaude側の設定を棚卸しし、Codex用AGENTS.mdへ移す計画を作る。

Claude Codeを使っていた人が最初に聞くのは「今まで作ったものはどうなるんですか？」です。答えは、捨てない。移します。

CLAUDE.md / skills / logs
棚卸し
残す / 直す / 捨てる
Codex側
AGENTS.md / skills / logs
そのまま移せる口調、判断軸、安全ルール、作業後レビュー、よく使う依頼。

Codex向けに直す「Claudeが」ではなく「Codexが」。Git運用と検証手順を明記する。

まだファイルは変更せず、まず移行計画だけ出してください。

文脈エンジンとして設計する

AGENTS.mdは「AIが最初に読む目次ファイル」として設計します。全部を詰め込まず、詳細情報は別ファイルに置いて必要な時だけ呼ぶ。これが Progressive Disclosure（段階的開示）の実践です。

ファイル内容なぜ分けるか読むタイミング
AGENTS.md目次・基本方針・安全ルール毎回読む定数。短くキープ常時
memory.md会社情報・顧客情報・長期知識業務依存で変わりにくい業務開始時
state.md今の重点テーマ・ブロッカー週次で変わる変数タスク開始前
contexts/brand-voice.md口調・文体・NGワードライティング時だけ読む文章生成時
contexts/philosophy.md価値観・判断軸・MVV重要判断時だけ読む意思決定時
「全部をAGENTS.mdに入れる」は禁物。インストラクション・バジェット（AIが安定して守れる指示量）は150〜200指示が限界。肥大化させず、目次から展開する設計にする。
Obsidian（任意） — これらのmarkdownファイルをGUIで管理・検索したい人向け。必須ではなく、Finderやエディタで管理しても同じ効果があります。使いたい場合は 事前準備ページ を参照。

まず空欄付きテンプレートとして作ってください。
下の「読む例」は、そのままターミナルで実行するものではありません。どんな粒度でAGENTS.mdに書くかを見る見本です。実際に作る時は、次の「Codexに貼る依頼」を使います。
読む例: AGENTS.mdの核
# AGENTS.md — 私のCodex運用ルール

## 基本方針
あなたは私の仕事を支援するAIエージェント。
目的は単発の回答ではなく、私の会社の仕事を前に進めること。

## 返答方針
- 前置きは短く、答えから入る
- 不明点は調べてから返す
- 判断が必要なときは筋良 / 筋悪を出す
- 成果物は「次に何をするか」まで落とす

## 判断軸
1. 顧客に価値が出るか
2. すぐ実行できるか
3. チームの手間が減るか
4. 将来の変更コストが低いか
5. 今完璧である必要があるか

## 安全ルール
- APIキー、パスワード、個人情報を外部に出さない
- メール送信、Slack投稿、SNS投稿は実行前に確認する
- ファイル削除、大量変更、上書きは実行前に確認する
- わからないことを断定しない。必要なら調べる

## 継続改善
同じミスを2回したらAGENTS.mdにルールを追加する。
同じ作業を3回やったらテンプレート化またはSkill化を検討する。
Codexに貼る依頼: 自分用に書き換える
上のAGENTS.md例を参考に、このフォルダの私用AGENTS.mdを作ってください。

必ずやること:
1. 私のIPOA、業務の目的、判断軸、安全ルールを空欄付きで入れる
2. 「毎回説明しなくてよい前提」と「今だけの状態」を分ける
3. APIキーや個人情報を入れない
4. 作成後、どこが仮置きで、どこを私が埋めるべきかを教える

まだ勝手に外部サービスへ送信しないでください。
動作確認
このフォルダのAGENTS.md、memory.md、state.mdを読んでください。
私の会社・役割・判断軸・あなたが手伝える仕事を要約してください。
ズレていそうなところがあれば、質問ではなく「仮説」として出してください。
6

Context7 / GitHub / Exa をMCPで取り込む

Codexのチャットから、外部の手と目を増やす。

あるあるAIが古い書き方でコードを書いて、あとで公式を見たら違う、という事故が起きる。
だからContext7、GitHub、ExaでCodexに最新情報を見る目を足す。
終わると勘や古い記憶ではなく、今の仕様と実リポジトリを見て進められる。
何が見えるようになるか最新ドキュメント、GitHub、Web検索を参照できる。
今やることconfig.tomlをCodexに作成・更新させる。
全員が同じようにできるかプレースホルダ方式なのでAPIキーを公開せず説明できる。

MCPは「Codexに目と手を増やす仕組み」です。Context7は最新ドキュメントを見る目。GitHubはリポジトリやIssueを見る目。ExaはWebやX由来の情報を探す目。Chrome DevToolsは作った画面を検証する目。これがないと、Codexは古い知識と手元ファイルだけで判断しがちです。

MCPが増やす「目と手」

function getItems() {
  const sheet = SpreadsheetApp.getActiveSpreadsheet().getSheets()[0];
  const values = sheet.getDataRange().getValues();
  const headers = values.shift();
  return values.map(row => {
    const item = {};
    headers.forEach((header, index) => item[header] = row[index]);
    return item;
  });
}

  • -s: AC電源接続時のスリープを防ぐ。
  • -u: ユーザー操作があった扱いにする。
  • -t 21600: 21600秒、つまり6時間。
GUIがよければ Amphetamine を使う。メニューバーから「指定時間だけ起動維持」を選べるので、講義中や長いCodex作業に向いています。

Claude Code Sub-agentsで作る

Claude Codeには「Sub-agents（Swarms）」機能があり、タスクを複数のエージェントに並列で分担させられます。

Sub-agent の特徴

リーダーエージェントが計画を立て、複数の子エージェントに並列で委任。コードを書く・調査する・検証するを同時進行できる。

Swarm の特徴

専門化したエージェントチームを生成。依存関係付きのタスクボードを共有し、並行作業して統合する。

grill-me結果から概要.mdを生成（Section 02の深掘り後に実行）

4. AIに任せたい作業トップ3
5. 判断が必要なポイント

作ったHTMLをAI自身に開かせ、現在地と改善点を画面ベースで確認する。

今やることagent-browserでサイトを開き、snapshotを取得する。
注意公開URLに秘密情報を載せない。ログイン画面や社外秘資料は扱いを分ける。
